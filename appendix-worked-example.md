# Appendix: worked example

A case study: **a long-running modeling-and-advice project**. The project models what each setting changes, from a read-only source of truth, recorded data and controlled tests, and aims at "work-then-advise": the human does ordinary work and the system says what to change and why, each claim a pre-registered, scored prediction. The human is also the blinded subject whose ratings some tests score. Patterns only: domain terms are kept only where an incident needs them, and the few counts quoted are the source project's, marked as such. No data values. The short commit hashes cited in the incident rows are deliberate: they refer to the source project's own history, which is not published here.

## 1. Setup as it ran

| Framework role | In the project | Start / end | Notes |
|---|---|---|---|
| Arbiter | an R&D session | own start command / the universal handoff command | orchestrator mode; owns the field dictionary, knowledge, evidence, tools, docs, the decision log; sole class writer; may fix any record |
| Operator | an applied-work interface session | own start command with a work-item argument / the universal handoff command | the human's interface for the applied work; writes per-item work folders and the human's preference model; may commit its own files |
| Thinker | an insight session (a different, scarcer model) | own start command / the universal handoff command; plus a free-form discussion command | briefed via committed files; commits only `HANDOFF.md` and its exposure log; never decodes raw data |
| Subagents | writers, code reviewers, robustness reviewers, predictors, blind scorers, readers | spawned by the Arbiter (and the Operator when approved) | ≤ 10-line returns; detail to files |

(Source session names are withheld; the framework templates use Arbiter / Operator / Thinker and role ids `arbiter` / `operator` / `thinker`.)

Supporting machinery: a commit helper holding a file lock (`flock`, intent-to-add for new files, `git commit --only`); a repo check with a scope list (out-of-scope warns, frozen blocks); a `Session-Role:` trailer; a decision log (tens of rows in the first weeks); a pending-blinded-steps list; an actor exposure log; hash-pinned scoring tools; an append-only "Review & corrections" table in the Arbiter's handoff. Peers found each other with Claude Code's `ListAgents` and messaged with `SendMessage` (both deferred tools, loaded through `ToolSearch`).

The roles evolved: the Operator role was first a single-purpose calculator session, then broadened; peer-to-peer messaging was first allowed only on the human's instruction, then made standing for the Arbiter after a day of smooth exchanges (about 20 leads relayed, source project count); the Thinker was added when insight work kept displacing record work. Each change of role had to invent its scopes, start command and handoff anew, which is why R1.9 and R1.10 now give the procedure.

## 3. Lessons learned

1. **Burden rules come from the human's frustration, quoted.** The strongest rules in the project (dose, states-changes, naming, discoveries-not-fear) were each one sentence from the human, recorded with the incident. Write them down the same day as memory entries with Why / How, and mirror them into the repository.
2. **Discipline that the human experiences as red tape gets reversed; discipline that guards a real failure survives.** Keep the rule's basis next to the rule so the difference is visible.
3. **The handoff is a product.** It needs a template, a heading contract, a verifier and a commit history that serves as its changelog. A handoff that is not verified drifts within two sessions; one that keeps its history in place becomes a log (incident #47).
4. **The blinded subject sees the whole window.** Every reply, tool output, subagent return, commit subject and shared document is a disclosure channel.
5. **Reviews earn their cost by withdrawing claims**, not by adding polish. Count withdrawn or downgraded findings as a success metric.
6. **One arbiter, many writers.** Letting the Arbiter fix peer records to standard (instead of bouncing them) removed a whole class of round trips.
7. **Cheap instruments first.** The fixed scripted actor and the on-disk backlog answered most leads without the human; the human's time was saved for tests only they could do.
8. **Start lean and add knobs on failure.** Budget gates for the Thinker were proposed and rejected ("we will self-limit as we run into issues"); none were ever needed.
9. **Investigate before testing.** A fixed, isolated, scored investigation phase replaced picking the favored explanation; its first run refuted two of the top hypotheses on hold-out data before any session with the human.
10. **Write the state, log the event.** The v1.3 contract (history blocks below each current block) was the pattern the source project had to dismantle: the files grew without bound and readers quoted superseded copies. A rewrite is safe only with a blind reverse-read, because the trim pass is where facts die (incidents #47, #48).
11. **The human's words are input, never the scope; blindness is physical, not instructed.** In applied work a review that only answers what was asked tells the human whether they are right and nothing more; and a blind analyst is blind only when the answer is in files it cannot open (incidents #65, #66).
12. **The deliverable comes first, and the cheapest design is asked for before the build.** A stage the human did not ask for that runs before their answer spends the budget they care about; the first design of a big build is often the thorough one (incidents #74, #83).
13. **Local history is proof, so publish a mirror.** A history rewrite breaks every hash that frozen records and pinned tools cite; a deterministic stripped mirror serves the public remote without touching it (incident #73).
14. **A checker that cannot fail on a positive duty passes everything.** A checker that only flags forbidden content, or counts a skipped item as a pass, certified a package whose half was undesigned; "no data" needs a search, and a repeated miss needs one root-cause pass and the smallest effective fix (incidents #95, #96, #101).
15. **A blind result is only as strong as its design order.** An analysis designed after the data are recorded recovered the right answer and still earns STRONG, not VALIDATED; a detector must beat its matched non-events before its parameters are tuned (incidents #106, #107).
